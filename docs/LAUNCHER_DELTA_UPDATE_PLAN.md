## 1.2.23 接入狀態

1.2.22 客戶端仍只會下載完整 NSIS 安裝檔，無法從伺服器單方面變成免安裝更新。因此 1.2.22→1.2.23 是一次核心橋接安裝。1.2.23 同時接入兩種更新途徑，但用途不同：

1. **介面與素材內容**：`launcher-content-v1.json` 由既有 Ed25519 信任金鑰簽署，只列本次要覆蓋的允許路徑；每個 blob 依 SHA-256 放在不可覆寫的物件路徑。客戶端核對清單簽章、版本／修訂、來源、大小與每檔雜湊，先寫入備用內容槽，全部驗證成功才切換；未列出的檔案仍使用安裝包。重新開啟啟動器後套用，下載或驗證失敗繼續用原版。只有 renderer UI 程式與本機媒體可進入此路徑，主程序、preload、Electron、安裝腳本與原生依賴不得覆蓋。正式 `/desktop/launcher-content-v1.json` 必須由 `server/desktop-distribution.js` 精確放行，並核對 Render 公開讀回與來源簽章完全一致。
2. **啟動器核心**：仍使用既有已簽署的 `launcher-release-v1.json` 與 NSIS EXE。新版可透過 `.exe.blockmap` 與本機已驗證舊 EXE 找出相同區塊，僅下載缺少區塊，重建後對整份新 EXE 檢查清單所載位元組數、SHA-256 及 PE 格式，再執行 NSIS。缺少舊 EXE、blockmap／Range 異常或驗證失敗就完整下載。這能減少傳輸量，**仍會執行安裝程序**。

1.2.22 EXE 的 blockmap sidecar 已上傳至相同版本 R2 路徑並完成公開 SHA-256 讀回；但 1.2.22 執行中的更新器不會使用它。1.2.21→1.2.22 的本機真實 EXE Range 重建測得只抓取 1,643,002 installer bytes、重用 264,637,419 bytes，並得到與簽署清單一致的最終 SHA；這是本機測試，不代表所有玩家的下載量。1.2.22→1.2.23 的真實 EXE 本機重建讀取 3,461,405 新位元組、重用 263,115,890 舊位元組；正式 1.2.23 EXE／blockmap 及 79,061 bytes 的一檔內容修訂已上傳 R2 並通過公開 SHA 讀回。Render 發行／內容清單的正式簽章與 SHA、下載頁已公開讀回；正式內容更新器從公開清單與 blob 只下載 79,061 bytes，啟用 revision=1。玩家舊版實機升級仍未驗證。

## 2026-10-02 原始 blockmap 方案與量測（歷史紀錄）

## 現況與目標

1.2.18 的三款遊戲程式與素材由桌面 CAS 按變更下載；啟動器自身則由 `desktop/launcher-update-service.js` 讀取 Ed25519 簽署的 `public/desktop/launcher-release-v1.json`，完整下載一個 NSIS EXE、核對位元組數與 SHA-256，再靜默執行。1.2.18 沒有差分程式，不能靠改伺服器清單就讓它只下載變更部分。

目標是讓支援差分的新版在更新啟動器時優先抓取變更區塊，保留現有簽署清單與完整 NSIS 安裝檔作權威來源和回退。更新後由啟動器自動重開；Windows 仍須在程式退出後替換安裝檔案，不能承諾完全不執行安裝程序。

## 已量測的機會與限制

- 使用本機 1.2.17、1.2.18 的 electron-builder `.exe.blockmap` 比對：1.2.18 安裝檔 268,390,665 bytes 中，266,207,343 bytes 的區塊可由 1.2.17 安裝檔重用，缺少區塊合計 2,183,322 bytes（約 0.8%）。這只是區塊重用量測，尚非實際網路流量或下一版本保證值。
- 1.2.18 的更新器單檔上限為 256 MiB（268,435,456 bytes），1.2.18 安裝檔僅剩 44,791 bytes 餘裕。第一個過渡版須先在實際封裝後確認低於舊版上限；不能只提高新版程式中的上限。
- 本機曾由更新器下載的 1.2.18 EXE 留在 `%APPDATA%\onepiece-tabletop-desktop\launcher-updates\<version>-<sha16>\`，並已核對正式大小與 SHA。全新安裝或清除快取的玩家沒有可重用的舊 EXE，需回退完整下載。

## 接入順序

1. 下一次內容版先加入差分下載能力，同時保留小於 256 MiB 的完整 NSIS EXE。現有 1.2.18 仍須依原流程完整下載這一次；避免為純過渡功能另發一次大檔更新。
2. 從該版起，每版將 EXE 與同名 `.exe.blockmap` 放在 R2 不可覆寫的版本路徑。`launcher-release-v1.json` 的 schema、Ed25519 簽章及完整 EXE 的 bytes／SHA-256 不變；舊客戶端仍可用完整檔更新。
3. 新客戶端先尋找並核對舊 EXE 快取，限制 blockmap 大小、格式、區塊數與 Range 請求；只接受 HTTPS、預期來源、精確 `206` 與 `Content-Range`。在暫存檔重建完整新 EXE，最後仍按已簽署清單核對完整 bytes、SHA-256 與 PE，成功後才交給現有 NSIS 靜默安裝流程。blockmap 不作信任根。
4. 缺少舊檔、區塊差異過大、Range 不支援、下載中斷或任何重建驗證失敗時，清除不完整暫存檔並自動回退完整 EXE。介面分開顯示實際下載量與更新進度，避免把重用的位元組誤報為已下載流量。

## 發布閘門

- 針對兩個正式版本的實際 EXE 做可重現的本機 Range 重建，所得完整 SHA 必須等於簽署清單；另測錯誤 blockmap、錯誤 Range、缺少舊檔、斷線及全量回退。
- 以已安裝的 Windows 1.2.18 執行一次過渡更新；下一次版本再實測差分更新、關閉程序、安裝路徑、卸載資訊、帳號與遊戲 CAS 保留、重啟及更新失敗後的回復。模擬 PE／spawn 的單元測試不能代替這項驗收。
- 公開 EXE／blockmap 先讀回大小與雜湊；正式 Render 簽署清單與來源逐位元組一致，舊版完整更新與新版差分／全量回退均通過後，才宣稱差分更新已部署。

以上為 2026-10-02 針對 1.2.18 記錄的原始 blockmap 方案；當時 1.2.18 仍是完整 EXE 更新，不能把該量測記為當時已上線的功能。
